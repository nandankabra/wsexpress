L0

Context diagram

The whole platform as one process. Four human roles sit outside the boundary, and an SMTP relay is the only external system the platform writes to. A guest never authenticates — a tracking ID alone buys a status reading, which is why public tracking is drawn as its own flow rather than folded into the customer's.

L1

Process decomposition

Process 0 opens into eleven processes behind a single gateway. Each owns exactly one data store and no process reads another's — the only way across a boundary is a labelled flow. The routes on each process are the gateway's real prefix table.

Three inter-process flows matter. Shipments asks Pricing for a quote; Pricing asks Location for country data over SOAP; and three processes push analytics events onto a fire-and-forget bus into CRM. Everything else is a process talking only to its own store.

L2

Explosion of 5.0 — create a shipment

The platform's densest path, top to bottom. It crosses four services, two database engines and both integration styles, and it is the flow where the resilience machinery is actually load-bearing.

Two details are easy to miss. The idempotency cache is an in-memory Map per process, not a shared store — a replayed Idempotency-Key is only recognised by the instance that first saw it. And flows 7 and 8 are drawn dashed because their breakers have fallbacks: with tracking-service stopped entirely, the shipment is still created and the customer still receives a 201.

Data stores

Polyglot persistence, one logical database per service. Nothing is shared: a service reaching another service's data does so through that service's API, never its store.
